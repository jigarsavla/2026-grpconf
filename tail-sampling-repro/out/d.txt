D2. THE ASK IS A96'S SHAPE AT A DIFFERENT OBSERVATION POINT
==============================================================================
  gRFC                 | A80 (In Review)                | A96 (merged 2025-07-01)                | this talk's ask                         
  -----------------------------------------------------------------------------------------------------------------------------------------
  what it measures     | per-WRITE socket latency       | per-CALL retry counts/delay            | per-MESSAGE first/gap                   
  observation point    | TCP socket (SO_TIMESTAMPING)   | the client call object                 | transport read boundary                 
  instrument type      | Histogram                      | Histogram x4                           | Histogram x2                            
  attribute set        | none / grpc.transfer_size      | grpc.method + grpc.target              | grpc.method + grpc.target + grpc.status 
  bucket boundaries    | unspecified                    | A66's latency boundaries (retry_delay) | A66's latency boundaries                
  default state        | off, sampled 1-in-1000         | experimental, off by default           | experimental, off by default            
  registers via        | A79 GlobalInstrumentsRegistry  | A79 (stated in the gRFC)               | A79 GlobalInstrumentsRegistry           

  A96 added four brand-new call-level histograms to gRPC, with exactly
  the attribute set the ask proposes, reusing A66's bucket boundaries,
  experimental and off by default -- and it is merged. The ask is not a
  new kind of thing. It is the same thing, one level further in.

  Also worth saying out loud: A96 exists because retry counts were
  unmeasurable from A66 alone. Emitted by grpc-python today: 0/4.

D3. THE AFFORDABILITY LEDGER -- real OTLP bytes for the two histograms
==============================================================================
  population: 462 real inter-message gaps + 6 real TTFMs
              gap p50 13.98 ms  p99 14.55 ms max 414.0 ms

   time series   no exemplars   with exemplars   exemplars carried   overhead
   --------------------------------------------------------------------------
          1         1,998 B         2,190 B                4        1.10x
         10        16,994 B        18,914 B               40        1.11x
        100       167,118 B       186,318 B              400        1.11x

   Both numbers are bounded by BUCKET COUNT x SERIES COUNT, not by
   observation count: the reservoir for an explicit-bucket histogram
   is 'always the number of bucket boundaries plus one', and it is
   reset every collection cycle. 41 boundaries -> at most 42 exemplars
   per series per interval, however many tokens you serve.
   Per RPC in this population: 365 B/RPC at 1 series.

D4. WHAT THE POINTER STORY COSTS -- tail sampling memory
==============================================================================
  one decode-heavy RPC = 5 spans = 850 B of OTLP trace data
  a tail sampler must HOLD that for decision_wait, per in-flight trace.

   num_traces   bytes held        note
   --------------------------------------------------------------
      50,000        42.5 MB     the Collector default
      10,000         8.5 MB     
       1,000         0.8 MB     

   And that is the OPTIMISTIC figure: it assumes 5 spans per trace.
   A per-message child span (an earlier lab costed it at 138.5 B/message) on a
   624-token generation is 78 more spans per trace.

   Compare with D3: the two histograms cost hundreds of bytes per
   export interval, flat in traffic. The expensive half of this
   architecture is the half that does not survive a long stream.
